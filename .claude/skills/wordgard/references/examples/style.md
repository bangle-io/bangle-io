# Example: Styling

Like everything else in the browser, the way a Wordgard editor looks
is determined by CSS styling rules. In order to support styles being
part of extensions, without the need arrange for loading separate CSS
files for every extension, the library uses a CSS-in-JS system for
automatically injecting styles bundled with the code they belong to.

You _can_ style the editor with regular CSS rules, as long as you keep
in mind that the styles provided via extensions have an extra class
selector added, which will make them more specific than your plain
rules unless you add some specific selectors yourself.

## Prefix Class

There are two types of style packages in this system—those that should
always apply, and those that should only apply when the _theme_ they
are part of is active. The former still need to be included in a
configuration (because that's how the editor makes sure they get
loaded), but they cannot be turned off and on by including or removing
the extension.

The first type is defined with {@link Wordgard.styles}:

```javascript
let styles = Wordgard.styles({
  ".my-widget": {
    border: "2px solid purple",
    backgroundColor: "orange"
  }
})
```

If you include that extension, a element with class `my-widget` inside
an editor will get the given style. You should target elements and
classes that are specific to your extension in such a set of styles,
so that they don't interfere with anything else.

For sets of styles that should be explicitly opted into, you use
{@link Wordgard.theme}:

```javascript
let theme = Wordgard.theme({
  "wg-content": {
    lineHeight: "1.6"
  }
})
```

Such a theme will only be active in editors that explicitly include
it. This is useful, because you don't want all editors in the document
to suddenly get a new line height when you use this theme in one
editor.

The way this works is that there is a {@link Wordgard.styleModule
facet} that controls which styles are loaded in the editor root
(window, frame, or shadow root). When you define a set of styles or a
theme, the returned extension includes a value for this facet.

All rules in such modules are prefixed with an additional class name
that is uniquely generated by the library. For regular style sets,
this class is stable, and always present on the editor. Themes get
their own class, which is only present on editors where the theme is
active.

Because these scope classes end up on the editor's outer element, if
your rules mention that element directly, you must tell the library
where to insert the class selector by including a `&` at the point
where it should appear. For example, this extension styles the editor
when it has a `faint` class.

```javascript
let faintSupport = Wordgard.styles({
  "&.faint": {opacity: "0.5"}
})
```

## Color Scheme

You can also use the special markers `&light` and `&dark`, which work
similarly but only match editors that use a light or dark {@link
Wordgard.colorScheme color scheme}.

By default, an editor uses a light color scheme. You can tell it to
use a dark scheme with `Wordgard.colorScheme.of("dark")`. But note
that this just toggles which of `&light`/`&dark` rules are used. The
default editor style does not contain rules that make the background
dark or the text color light in a dark color scheme—you'll have to
take care of that yourself, either by making sure the colors cascading
from the editor's parent elements fit the scheme, or by directly
providing the needed styles as an extension.

Or, if your page is already using the CSS
[`prefers-color-scheme`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-color-scheme)
feature, you can configure your editor with
`Wordgard.colorScheme.of("auto")` to make its color scheme
automatically follow the preferred scheme.

## Rule Notation

As you could see in the examples so far, styles are provided in some
kind of bastardized JavaScript-object CSS notation. The object you
give to {@link Wordgard.styles} or {@link Wordgard.theme} contains
selectors as property names, and objects that define style properties
as their values. The property names can use camel-case, which will be
normalized to CSS dash notation (`fontFamily` → `font-family`).
Property values should be strings.

It is possible to nest rules by including properties with a `&` marker
inside of these properties, like this:

```javascript
let myPanelStyle = Wordgard.styles({
  "wg-panel.my-panel": {
    borderBottom: "2px solid black",
    "& p": {
      padding: "0 10px"
    }
  }
})
```

This styles paragraphs inside `my-panel` panels with a small
horizontal margin.

You can also wrap some rules in some types of `@` blocks, like this:

```javascript
Wordgard.theme({
  "@media screen and (min-width: 400px)": {
    "wg-content": {
      fontSize: "2rem"
    }
  }
})
```

## DOM Structure

The editor's outer element has a `<wordgard-editor>` tag name, though
you'll usually want to target it with the `&` selector in your rules.
This is a vertical flexbox that holds the {@link Wordgard.scrollDOM
scroller element}, {@link Panel panels}, and {@link Tooltip tooltips}.

The scroller is a `<wg-scroller>` element. By default, it doesn't
actually scroll, but styling this element is the way to make an editor
that has its own scroll bar (for example via {@link
Wordgard.scrolling}).

Inside of that is the {@link Wordgard.contentDOM `<wg-content>`}
element that holds the actual editable document. This element has
[`contenteditable`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/contenteditable)
enabled, as well as a number of editing-related attributes like
`role="textbox"`, and is the element that has focus when the editor
content is focused.

There's also a `<wg-cursor-layer>` element in the same parent as the
content, which overlays it and is used to draw the custom cursor as a
`<wg-cursor>` element.

There are extensions for adding attributes to the editor's {@link
Wordgard.editorAttributes outer} element and {@link
Wordgard.contentAttributes content} element. These can be useful for
adding classes to influence styling in specific circumstances, based
on editor state.

The editor content can be styled by targeting the elements {@link
Node.Spec.shape used} to draw it. There are some assumptions the
editor makes about its content's layout though, which you should take
care not to violate. For one thing, inline content is expected to
render as inline elements (so don't set your textblocks to `display:
flex` or something like that), and blocks should lay their content out
in one direction, and if that direction isn't vertical, declare
themselves to have {@link Plot.Type.orientation row orientation}.

The editor's own styles define a few CSS variables that may be useful
in custom styling:

 - `--wg-highlight-color` is the color used for selected elements and
   focus rings. It is a bright blue by default.
 - `--wg-dialog-font` is a `font` style used in dialogs and tooltips.
 - `--wg-border-color` is the color used for borders around the editor
   and its interface elements.
 - `--wg-panel-color` is the background color of {@link Panel panels}
   and {@link Tooltip tooltips}.
